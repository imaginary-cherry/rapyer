<objective>
Fix the model-level cascade-trigger gate so `refresh_ttl()`/`aset_ttl()`/`asave()` actually invoke the cascade Redis Function for parents whose ONLY cascade edge is an SF-held-ref field. Today `_contains_foreign_key()` (`rapyer/base.py:249-250`) returns `bool(cls._relational_field_names or cls._contain_fk)` — both sets are populated from inline-JSON-document FK shapes only, and `RedisSet`/`RedisPriorityQueue.contains_fk_field()` is hardcoded `False` (Phase-1-locked), so an SF-only parent's `_contains_foreign_key()` is `False` and the public API silently takes the native-EXPIRE fast path, never firing 02-01's new Lua traversal.

Purpose: 02-01 proves the Lua Function follows SF-held-ref edges when called directly via `FCALL`. Without this fix, that traversal is unreachable from the public API (`asave()`, `aset_ttl(cascade=True)`, `refresh_ttl()`) for any parent whose sole cascade edge is SF-held — the feature would be dead code for the exact usage CASF-04/05/06 describe ("when a cascade fires on a parent"). This plan closes that gap additively, without touching the Phase-1-locked `contains_fk_field()` or `__init_subclass__`.
Output: A new public classification helper in `rapyer/cascade/planner.py`, a lazily-cached classmethod + one-line `_contains_foreign_key()` change in `rapyer/base.py`, a mock-based unit test proving the gate flips correctly (and stays unchanged where it must), and a real-Redis :6370 integration test proving the whole public API path end-to-end.
</objective>
