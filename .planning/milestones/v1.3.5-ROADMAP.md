# Roadmap: rapyer — Configurable TTL Cascade

## Overview

This milestone adds the first slice of a configurable cascade framework to `rapyer`: setting a parent aggregate's TTL performs a **cascading refresh** across its cascade-enabled `ForeignKey`-referenced children — each child re-armed to **its own `Meta.ttl`** — applied atomically and server-side at set-time. The journey follows the hard dependency chain surfaced by research — build the pure-Python backbone first (config surface + FK-graph field classification), then land the flagship server-side unit: **one Lua script that both traverses the FK graph and expires the reached keys** (its per-class plan table baked in at `SCRIPT LOAD` from Phase-1 classification), then wire cascade into the real write path without disturbing existing TTL behavior, and finally prove it end-to-end on real Redis with docs and extensibility stubs. Every risk class (fragile `__init_subclass__`, traversal logic, Lua/fakeredis divergence, the fragile TTL/action surface) is isolated into the phase that can be tested against the pitfall that threatens it. Cascade ships opt-in and disabled-by-default, so existing projects are byte-for-byte unaffected.

> **Phase-2 re-architecture (2026-07-07):** traversal moved from the Phase-1 Python `CascadePlanner` **into the Lua script** (discovery + apply now one atomic op, D-01); TTL semantics became a **per-child cascading refresh** (each child reset to its own `Meta.ttl`, D-04) applied via plain relative `EXPIRE` (no `GT`/`NX`, so no Redis-version spike — D-05). `CascadePlanner.atraverse` is demoted to generating the baked plan table + the EXT-01 seam (D-03). See `phases/02-atomic-ttl-apply-spike-then-implement/02-CONTEXT.md`.

## Phase Details

### Phase 1: Cascade Config + Cycle-Safe Traversal Backbone

**Goal**: The full "which keys does a cascade touch" pipeline exists in debuggable, unit-testable Python — cascade config is declared and detected, and an operation-agnostic planner walks the cascade-enabled `ForeignKey` graph cycle-safely to a configured depth, emitting a de-duplicated flat key list. No TTL is applied yet; the extensible seam (shared traversal, swappable apply) is established here.

> **Superseded scope note (Phase-2 re-architecture, D-03):** `CascadePlanner.atraverse` (the runtime BFS delivered here) is **no longer the TTL runtime path** — Phase 2 moves traversal into the Lua script. This phase's lasting deliverables are the config surface + FK-graph field classification (which now feed the baked-in Lua plan table) and the `CascadeSpec`/`CascadePlanner` EXT-01 seam retained for future delete/save cascade. Left as delivered for the record.
**Depends on**: Nothing (first phase)
**Requirements**: CFG-01, CFG-02, CFG-03, CFG-04, CASC-03, CASC-04, EXT-01, COMPAT-02
**Success Criteria** (what must be TRUE):

  1. A developer can declare `Annotated[Reference[T], CascadeTTL(...)]` on an FK field and it is detected into `_cascade_ttl_fields` via an additive `__init_subclass__` branch; existing plain `ForeignKey` declaration and `afetch`/`aget` usage are unaffected (CFG-01, COMPAT-02)
  2. `init_rapyer(cascade_ttl=...)` sets a global default that ships **disabled by default**, and a per-field `CascadeTTL` overrides it with documented precedence field > global > off; `CascadeTTL` exposes `enabled`/`depth`/`mode` (a `TTLCascadeMode` enum) with sensible defaults (CFG-02, CFG-03, CFG-04)
  3. `CascadePlanner.atraverse(root_key, root_cls)` (a-prefixed per the project's Redis-round-trip naming convention) follows cascade-enabled FK edges to each field's configured per-subtree `depth` budget and returns a de-duplicated flat key list that includes each reachable child's own special-field keys (via `_all_keys_for_key`, no leaf fetch) (CASC-03)
  4. Traversal terminates cleanly on cycles, self-references, diamond graphs, and dangling/missing children via a visited-set (the primary termination guarantee, D-05) plus an optional per-subtree `depth` ceiling; the root key is never double-collected (CASC-04)
  5. The planner is operation-agnostic (a `CascadeSpec` ABC with `CascadeTTL` as one strategy and traversal decoupled from any leaf action), so delete-cascade and save-cascade can plug in later by swapping only the apply (EXT-01)

### Phase 2: Atomic TTL Apply (Spike then Implement)

**Goal**: One registered `cascade_ttl_apply` Lua script performs the **entire** cascade server-side — traversing the cascade-enabled FK graph (`JSON.GET` per node → `cjson.decode` → visited-set dedup → per-subtree depth budget) **and** re-arming each reached key to its owning class's own `Meta.ttl` — as one atomic operation. The per-class plan (special-key suffixes + FK edges) is baked into the script at `SCRIPT LOAD` from Phase-1's field classification (mirroring the SF-dispatch injection). The user-supplied prototype `reference/cascade_ttl.lua` is the concrete design target — port/adapt it, don't design from scratch. The original risk spike collapses to a confirmatory dual-backend parity test (relative `EXPIRE` needs no version-gated flags).
**Depends on**: Phase 1
**Requirements**: CASC-02, CASC-05, CASC-07
**Success Criteria** (what must be TRUE):

  1. A confirmatory dual-backend test proves fakeredis and real Redis agree on the traversal reads (`JSON.GET` output shape → `cjson.decode`); the cascade Lua path is marked integration-only only if fakeredis genuinely diverges — no `GT`/`NX` version spike is needed (relative `EXPIRE`, D-05)
  2. `cascade_ttl_apply.lua` traverses the cascade-enabled FK graph **and** applies each reached key's owning-class `Meta.ttl` via relative `EXPIRE`, as one atomic server-side operation — discovery + apply together, no partial/interleaved application, no TOCTOU (CASC-02, D-01/D-04)
  3. The per-class plan table (`--[[CASCADE_PLAN_TABLE]]`) is generated from Phase-1 classification and baked at `SCRIPT LOAD` (mirroring `_inject_sf_dispatch`); `TTLCascadeMode` stays a single-member `EXTEND` seam — no `OVERWRITE`/`IF_UNSET`, no `GT`/`NX` (CASC-05, D-02/D-06)
  4. A cascade-reachable target with `Meta.ttl is None` raises at `init_rapyer()` (fail-fast), after FK-target resolution and per-model TTL assignment (CASC-07, D-08)
  5. The script is registered in `SCRIPT_REGISTRY` with a name constant and invoked only via `run_sha`/`arun_sha`, inheriting NOSCRIPT self-heal, and survives the existing `flush_scripts` fixture

**Research**: light — the user-supplied prototype (`reference/cascade_ttl.lua`) is the concrete design target and already claims verified `JSON.GET` parity; the original MEDIUM-confidence spike collapses to a confirmatory dual-backend test (no `GT`/`NX` version question remains, per D-05).

### Phase 3: Action-Boundary Wiring + Backward-Compat Regression

**Goal**: Connect the planner and apply into the real write path so that setting or refreshing a cascade-enabled parent's TTL propagates atomically to all cascade-enabled children (including their own special-field keys), riding the triggering write's existing transaction — while the no-config path stays byte-for-byte unchanged.
**Depends on**: Phase 2
**Requirements**: CASC-01, CASC-06, COMPAT-01
**Success Criteria** (what must be TRUE):

  1. A cascade-enabled parent's `aset_ttl`/`refresh_ttl` expires the parent's own keys **plus** every cascade-enabled referenced child's keys — including each child's own special-field keys — in one atomic operation (CASC-01)
  2. Cascade rides inside the triggering write's existing `ensure_pipeline` MULTI/EXEC, resolving through `resolve_root_model` and reusing existing special-field iteration — it never re-implements root/special-field key resolution and never leaks a pre-pipeline `afetch` loop (CASC-06)
  3. With no `CascadeTTL` configured anywhere, existing `Meta.ttl`/`refresh_ttl` behavior is byte-identical and the `refresh_ttl`-excludes-`DELETE` rule is unchanged; the existing TTL suites and `TwoModelDeleteBase` pass unmodified (run as the regression gate first) (COMPAT-01)
